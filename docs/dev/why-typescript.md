# 为什么用 TypeScript

先说结论：**JavaScript 也能写，而且跑得一样好；但 TypeScript 能让你少踩坑。**
我们的模板、示例、CI 全部按 TypeScript 配好，你顺着写就行，不用自己搭环境。

## 两种写法的真实差别

| | JavaScript | TypeScript |
| --- | --- | --- |
| 上手成本 | 零，直接写 | 多一个 `npm run build`，其余一样 |
| 参数写错、字段拼错 | 上线后运行时才炸 | 编辑器里当场标红 |
| 用别人写的模块 | 靠读文档猜结构 | 有类型提示，能跳转定义 |
| 重构 | 改一个名要全局搜 | 改名、改签名，编译器帮你找漏 |
| 交付产物 | 直接是 `.js` | 编译出 `.js`，产物一样是纯 JS |

关键在最后一行：**你写的是 TS，跑的是 JS**。宿主拿到的永远是编译后的单文件，
所以「用 TS」不会给用户增加任何运行时负担，也不会引入额外依赖。

## 「类型没错就基本没错」是什么意思

我们给宿主 API 写了类型声明，`api.tool()`、`api.route()`、`api.log` 这些调用，
参数结构、返回值形状都有约束。类型检查通过意味着：

- 你调的方法真实存在
- 你传的字段名拼对了
- 你返回的结构和宿主期望的一致

剩下的只有**逻辑**问题 —— 这已经比「字段名打错，上线才发现」省太多时间。

```bash
npm run check     # 只做类型检查，不产出文件，改一行跑一次很快
npm run build     # 真正编译，产物进 lib/ 和 dist/
```

## 什么时候可以不用

- 几十行的小脚本，只调一两个接口
- 你不打算长期维护，也不给别人用

即便这样，也建议用模板仓库开局 —— 目录结构、`package.json` 字段、发版流程都是现成的，
把 `.ts` 写成 `.js` 一样能跑，只是失去类型检查。

## 环境要装什么

```bash
npm install -D typescript @types/node
```

模板里已经写好了 `tsconfig.json`（后台，`src/` → `lib/`）和 `tsconfig.client.json`
（面板，`client/` → `dist/`），不用自己调。

目录怎么摆见[插件结构](/dev/anatomy)，怎么发版见[构建与发布](/dev/build-release)。
